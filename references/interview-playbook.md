# 提问手册 · 决策树、前沿与轮次

这份手册展开 `SKILL.md` 里的机制。它解决三个问题：

1. 什么问题值得问；
2. 什么时候问；
3. 一轮问多少、怎么问。

## 1. 决策树

把原始问题改写成一句“这次要做的决定”，这就是根节点。例如：

> 原始问题：帮我做个 AI 周报工具。

根节点不是“做一个工具”，而是：

> 这次要决定：第一版周报工具为谁、解决哪一个最痛的动作、用什么最小方案验证。

根节点下面按六个固定分支展开：

| 分支 | 要落定的问题 |
|---|---|
| 目标与价值 | 做完之后谁的生活/工作发生什么变化；为什么现在做 |
| 现状与事实 | 现在怎么做；最痛的一步；已有数据和系统 |
| 范围与非目标 | 这次包含什么；明确不做什么 |
| 约束与资源 | 时间、钱、技术栈、人、合规 |
| 验收与证据 | 什么证据算成功；谁来验收 |
| 风险与可逆性 | 选错的代价；多久能改回来 |

每个分支继续挂子决策。例如“范围”下可能挂：

- 只做单人版还是团队版？
- 只读汇总还是自动写回？
- 先接哪些数据源？

### 节点状态

- **已定**：用户明确回答，或事实已经排除其他选项；
- **前沿**：所有前置节点已定，但自身未定；
- **未解锁**：还有前置节点未定；
- **未知**：需要事实或实验才能定，不是靠问。

只有“前沿”能进这一轮。

## 2. 前沿与轮次

### 前沿

前沿 = 当前所有“前置已定、自身未定”的决策集合。

判断一个节点能不能问：

- 它依赖的每个决定都有答案了吗？
- 答案不依赖本轮其他问题的结果吗？
- 它真的会改变方案、范围、验收或授权吗？

三个都是“是”，才能进本轮。

### 为什么一轮问整个前沿

一次只问一个问题，会把同一层的信息拆成很多轮，用户疲劳，模型也容易在等待中丢失上下文。一次问整个前沿，可以让用户在少数几轮里答完一层。

### 为什么又限制 5 个

前沿可能很大。一轮十几个问题，用户会开始敷衍，答案质量下降。

规则：

- 前沿 ≤5：全问；
- 前沿 >5：按“影响 × 不可逆性”排序，先问前 5 个；
- 明确告诉用户还有几个留到下一轮；
- 有依赖关系的问题不能拆到同一轮。

排序时问自己：

- 这个答案会改变目标吗？（影响最大）
- 选错以后还能改吗？（不可逆性最高）
- 它会影响后面多少个问题？（杠杆最大）

### 轮次模板

```text
本轮前沿 3 个；另有 2 个依赖本轮答案，下一轮再问。

❓ **Q1 — 为谁做**：第一版的直接用户是谁？

A. 你自己
B. 你的直属团队（3–8 人）
C. 整个部门（20+ 人）

➡️ 推荐：A。默认：A（未答时采用）；猜错代价：范围扩大 3 倍，第一版延期。

---

❓ **Q2 — 最痛的动作**：现在周报最耗时间的是哪一步？
...
```

## 3. 事实 vs 决定

### 事实：自己查

事实是环境可以回答的：

- 代码里有没有某个接口；
- 某个库的版本；
- 竞品是否支持某功能；
- 用户过去的周报长什么样；
- 某个命令是否存在。

处理方式：

- 读文件、跑命令、查文档、搜网络；
- 需要大范围探索时，派子 agent 去查，不要阻塞不相关的问题；
- 查不到就标“待证”，不要编。

### 决定：用户做

决定是价值判断：

- 先做 A 还是 B；
- 接受多大风险；
- 牺牲速度还是范围；
- 要不要花这笔钱；
- 能不能动别人的数据。

处理方式：

- 放进前沿，给选项和推荐；
- 等用户回答；
- 不替用户拍板；
- 用户不答，不等于同意，除非是低风险可逆细节且已说明默认。

### 预测：标成假设

“这个方案大概两周能做完”不是事实，是预测。写成“假设：两周，未验证”，并说明猜错的代价。

## 4. 问题类型

### 目标类

- 做完之后，什么会不一样？
- 如果只能成功一件事，是哪件？
- 为什么是现在，而不是下个月？

### 现状类

- 现在这件事怎么做？
- 最痛的一步是哪一步？
- 有没有现成的数据、脚本、模板？

### 范围类

- 这次明确不做什么？
- 第一版最小可用的边界在哪？
- 哪些人/系统不在这次范围？

### 验收类

- 什么证据能让你说“成了”？
- 谁来验收？
- 如果只能看一个指标，看哪个？

### 约束类

- 时间、钱、人、技术栈，哪个是硬约束？
- 哪个约束可以先松？

### 风险类

- 选错的代价是什么？
- 多久能改回来？
- 最坏情况下，损失上限是多少？

### 授权类

- 哪些动作需要你点头？
- 哪些可以自主决定？
- 能不能动生产数据/别人的账号/预算？

## 5. 答“不知道”怎么办

“不知道”是有效答案，不是失败。处理顺序：

1. 判断这是事实未知、预测未知，还是偏好未知；
2. 事实未知：去查；
3. 预测未知：设计最小实验/原型；
4. 偏好未知：给 2–3 个具体场景让对方选，而不是抽象追问；
5. 仍然不知道：按默认走，记账，标明代价。

## 6. 不可 grill 的问题

有些问题靠谈话解决不了：

- 界面好不好看；
- 交互手感；
- 市场会不会买；
- 真实负载下的性能；
- 团队愿不愿意用。

遇到这类问题，停止提问，做一个**廉价可反应物**：

- 手绘/线框；
- 一次性原型；
- 三张风格不同的样图；
- 一个 50 行的脚本；
- 一个小范围试用。

让对方对具体东西说“是/不是”，比继续问抽象问题有效。

## 7. 范围太大

症状：

- 一轮问不完；
- 问题开始重复；
- 用户回答越来越短；
- 决策树越铺越宽。

处理：

1. 先把大问题拆成 2–4 个独立子问题；
2. 选一个先 forge；
3. 其余标记“后续”，不在本轮展开；
4. 如果子问题之间强耦合，先问“先做哪一个”的排序问题。

## 8. 用户变得被动

信号：

- “都行”“你定”“随便”；
- 连续对推荐说“可以”；
- 不提供新信息。

处理：

- 不要把这当成授权；
- 切换 One-shot：给一套默认方案，逐条标假设和代价；
- 请用户只确认“范围 / 验收 / 不可逆动作”三类；
- 其余默认项写进台账，标明“未确认”。

## 9. 问题质量检查

一个合格的问题：

- 只问一个决定；
- 有 2–4 个真实可选、互斥的选项；
- 有推荐答案；
- 有默认值和猜错代价；
- 答案不依赖本轮其他问题；
- 回答者掌握回答所需的信息；
- 答案会改变方案。

不合格的问题：

- “你觉得怎么样？”（没有选项，没有决定）
- “要不要考虑一下性能？”（不影响当前决定）
- “你的 API key 是多少？”（事实，自己能查/不该问）
- “先做 A 还是先做 B？顺便 UI 用什么颜色？”（两个决定混在一起）
- “如果选 A，那 B 怎么设？”（依赖未答问题）

## 10. 收尾

前沿清空后，不要直接开工。做三件事：

1. 输出 Forged Question；
2. 输出决策台账和未知项；
3. 请用户确认共享理解。

确认后，才进入执行或 Brief 模式。
