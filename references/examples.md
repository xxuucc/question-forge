# 前后对照 · 三个完整例子

## 例 1：Forge 模式（产品/工具）

### 原始问题

> 帮我做个 AI 周报工具，越快越好。

信息缺口扫描：

| 缺口 | 状态 |
|---|---|
| 谁用 | 未知 |
| 现在怎么做 | 未知 |
| 最痛的一步 | 未知 |
| 数据源 | 未知 |
| 成功标准 | 未知 |
| 时间/预算 | 只有“越快越好” |
| 已试过什么 | 未知 |

### 第 1 轮

```text
本轮前沿 4 个；另有 3 个依赖本轮答案，下一轮再问。

❓ **Q1 — 为谁做**：第一版的直接用户是谁？

A. 你自己
B. 你的直属团队（3–8 人）
C. 整个部门（20+ 人）

➡️ 推荐：B。默认：B（未答时采用）；猜错代价：范围扩大或缩小，直接影响数据源和权限设计。

---

❓ **Q2 — 最痛的动作**：现在写周报，最耗时间的是哪一步？

A. 收集本周做了什么
B. 判断哪些值得写
C. 组织成文/排版
D. 发给领导后的反复修改

➡️ 推荐：A。默认：A；猜错代价：做出来的功能不是第一痛点，白做一版。

---

❓ **Q3 — 数据源**：第一版允许接哪些数据？

A. 只接本地 Git 提交
B. Git + 任务系统（Jira/Linear）
C. Git + 任务系统 + 聊天记录
D. 先手动粘贴，不接系统

➡️ 推荐：A。默认：A；猜错代价：接太多源，第一版延期；接太少，价值不足。

---

❓ **Q4 — 成功标准**：第一版上线后，什么证据算“成了”？

A. 你自己连续用 2 周
B. 团队 3 人连续用 2 周，周报时间减半
C. 领导说“以后就这么交”

➡️ 推荐：B。默认：B；猜错代价：验收标准太松，做出来没人用。
```

### 用户回答

> 1B，2A，3A，4B。另外不要接聊天记录，合规过不了。

### 第 2 轮（只问被解锁的）

```text
本轮前沿 2 个；另有 1 个依赖本轮答案，下一轮再问。

❓ **Q5 — 输出形态**：周报最终以什么形式交付？

A. Markdown 文件
B. 飞书/Notion 页面
C. 邮件正文

➡️ 推荐：A。默认：A；猜错代价：如果团队用 Notion，还要重做集成。

---

❓ **Q6 — 人在回路**：生成后要不要人工确认再发？

A. 必须人工确认
B. 直接发，事后可改
C. 只生成草稿，不负责发

➡️ 推荐：A。默认：A；猜错代价：自动发错内容，信任一次就没了。
```

### 收敛输出（节选）

```markdown
## 锻造后的问题

**一句话**：为 3–8 人团队做一个基于 Git 提交的 AI 周报工具，第一版只解决“收集本周做了什么”，人工确认后输出 Markdown，用 2 周内周报时间减半来验收。

**背景与现状**：团队目前手工回忆 + 翻 Git；最痛的是收集，不是写作（用户确认）。

**目标**：把每周收集素材的时间从约 2 小时降到 1 小时以内。

**成功标准**：3 名团队成员连续使用 2 周；周报准备时间减半；无合规事故。

**范围**：包含 Git 提交采集、AI 归纳、Markdown 草稿、人工确认；不包含聊天记录、Jira、自动发送。

**约束**：第一版 2 周内可用；不接聊天记录（合规）；只读 Git，不写回仓库。

**关键假设**：假设团队都用同一个 Git 仓库（未确认）；假设提交信息足够生成周报（未确认）。

**待确认**：仓库是否统一；提交信息质量是否够；谁来做最终验收。

**下一步**：产品负责人 3 天内确认仓库范围；工程 2 周内出第一版。
```

决策台账：

| # | 决定 | 结论 | 依据 | 谁定的 | 置信度 |
|---|---|---|---|---|---|
| D1 | 用户 | 3–8 人团队 | 用户 | 用户 | 高 |
| D2 | 第一痛点 | 收集素材 | 用户 | 用户 | 高 |
| D3 | 数据源 | 只接 Git | 用户 | 用户 | 高 |
| D4 | 验收 | 3 人 2 周，时间减半 | 用户 | 用户 | 高 |
| D5 | 输出 | Markdown | 推荐默认 | 我 | 中 |
| D6 | 人工确认 | 必须 | 推荐默认 | 我 | 中 |

## 例 2：One-shot 模式（直接改写 prompt）

### 原始问题

> 帮我写个爬虫，抓点数据，最好快一点。

### 锻造后的问题

```markdown
## 锻造后的问题

**一句话**：写一个一次性 Python 爬虫，抓取 `<目标站点>` 的 `<字段>`，输出 CSV；只抓公开页面，遵守 robots，限速 1 req/s。

**背景与现状**：需要一份结构化数据做分析；目标站点未指定；字段未指定；数据量未知。

**目标**：拿到一份可直接分析的 CSV，而不是一套爬虫框架。

**成功标准**：CSV 包含 `<字段 1/2/3>`；行数与页面列表一致；重复运行结果稳定；不触发封禁。

**范围**：包含列表页 + 详情页抓取、去重、CSV 导出；不包含登录态、验证码、代理池、分布式。

**约束**：一次性脚本；Python 3.11+；只使用 requests/BeautifulSoup；总运行时间 <10 分钟。

**关键假设**：
- 假设目标站点无需登录（未确认）；
- 假设字段在 HTML 里可直接解析（未确认）；
- 假设数据量 <1 万行（未确认）。

**待确认**：
1. 目标站点 URL 与字段；
2. 是否需要登录；
3. 数据用途与保留期限。

**下一步**：用户给出 URL 和字段后，先抓 1 页样本确认结构，再写全量。
```

注意：这里没有假装知道 URL 和字段；把信息缺口变成“待确认”，而不是编一个。

## 例 3：Brief 模式（交给执行 agent）

Forge 收敛后，用户说：“把它写成任务书，让 agent 自己跑。”

输出结构：

```markdown
## 任务书（节选）

这活为什么干：团队每周花 2 小时翻 Git 写周报，目标是减半。
冲突时让步顺序：数据正确 > 覆盖全 > 速度快。

### 我替领导拍的板

| 问题 | 默认值 | 猜的 | 猜错代价 |
|---|---|---|---|
| 输出格式 | Markdown | 是 | 要改 Notion 集成 |
| 提交信息清洗 | 保留原文 | 是 | 周报语气偏工程化 |

### 界限

只允许改 `tools/weekly/` 和 `tests/weekly/`；其余只读。
验收脚本 `tests/weekly/accept.sh` 不许改。

### 现状与任务 0

实测：仓库 12 个，周均 87 次提交；`gh` 命令存在。
任务 0：跑 `./scripts/check_env.sh`，核对上面数字；对不上写 `BLOCKED.md` 并停。

### 任务 1

目标：从 12 个仓库采集最近 7 天提交，生成 `weekly.md`，包含每人 3–5 条要点。
验收：`./tests/weekly/accept.sh` 退出 0，且 `weekly.md` 中 12 个仓库各至少 1 条；跳过 0。
反向验证：故意删一个仓库配置，确认脚本变红，再还原。

### 完成条件

1. `accept.sh` 全绿，且 3 名团队成员试用后确认可用；
2. 除 `tools/weekly/` 与 `tests/weekly/` 外，`git diff` 为空。
每条都要在对话里贴实际命令输出；只说做完了不算。
```
