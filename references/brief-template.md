# Brief 模板 · 把锻造后的问题交给执行 agent

只有用户明确要“给 agent 写任务书 / 让它自己跑”时，才使用本模板。先完成 Forge 收敛；没有共享理解，不写 brief。

结构参考了 khazix 的 `leader` skill（MIT），并按 Question Forge 的决策台账做了衔接。整份 ≤4000 字符；单任务通常 1500–2000。

## 结构

顺序固定：「我替领导拍的板」放最前，领导发出前扫一眼就能改判；「完成条件」放最后，两条硬指标收拢一切。

### 开头（不带标题，五件事各一句）

- 这份文档定义本次任务，服从用户和宿主的授权边界；拿不准的写进 `BLOCKED.md`，跳过继续做别的，最后随交付提交。
- 断了、换新会话：先读 `PROGRESS.md` 接着做，别重做；每做完一项立刻更新。
- 这活为什么干：一句意图——为什么干、干完世界什么样。书里没写到的情况，执行者靠它自己裁。
- 两个要求打架时的让步顺序（例如「算得对 > 做得全 > 做得快」）。
- 死规矩与参考的分界：「只允许」「不许」违反算失败；「建议」有更好的路就走，在 `PROGRESS.md` 记一句为什么。

### 我替领导拍的板

没问出口的每个决定一行：

| 问题 | 默认值 | 是否猜的 | 猜错代价 |
|---|---|---|---|
| … | … | 是/否 | … |

领导发出前可改。只在已有授权内采用默认值；**沉默不是授权**。写不出机器可判命令的目标（文风、体验类）也记在这里：改成抽查点 + 领导亲验，注明这活只能半托。

### 界限

- 白名单：只允许改哪些路径、新建哪些文件，其余只读。用白名单，不用黑名单。
- 判卷标准（测试、验收脚本、CI 配置）碰都不许碰；无 git 时给每个文件的 sha256 指纹。
- 点名最诱人的顺手活（一行就能修的 bug、顺手重构、顺手装工具），写明进 `BLOCKED.md` 待裁决。
- 缺少明确授权或范围不清的操作（删数据、改权限）停下写 `BLOCKED.md`，做别的。

### 现状与任务 0

- 实测数字逐条带来源与日期；查不到的标「猜的，没验证」。
- 能提前实证的关键结论写进来，提前拆掉借口。
- 任务 0：跑指定命令核对上面的数字。不存在的命令、空转的假检查当场记 `BLOCKED.md`；对不上就停，证据写 `BLOCKED.md` 最上面，只做不受影响的部分。
- 核对无误后，把「理解的目标 / 顺序 / 最大风险」≤10 行写进 `PROGRESS.md` 再动工。

### 任务 N

每个任务包含：

- 一句话目标，带数字；
- 从哪下手一句；多任务按依赖排序，说清为什么它排前面；
- 死规矩写成「做 A，否则 B」，带具体后果；
- 验收 = 实际触发目标行为 + 断言关键结果或产物，不能用源码 grep 或空转退出码代替功能验证；纯文本、lint 等按检查本身的语义验收；
- 命令 + 机器可判的判定（含防漏判定，如「跳过 0」）；
- 反向验证 = 故意制造一次失败、贴变红输出、还原后贴全绿。凡是「坏了没人会知道」的检查都要这一步。

### 规矩

- 防作弊点名到具体姿势：跳过测试（skip/todo）、放宽判断、把被测对象换成假的（mock）、删测试、改阈值或验收脚本、`|| true`——全算失败；测试数 / 覆盖率只许 ≥ 基线；补测试类任务加「实现目录 `git diff` 为空」。
- 不新增流程、权限、依赖；必须加的写 `BLOCKED.md`。
- 同一条验收连败 3 次换下一项；结果比开工差就回滚如实报告——「没做成但说清了」合格，「做了但更糟」不合格。
- 项目自有纪律（分支 / PR 规则、提交前检查）写在这里。

### 完成条件

- 两条硬指标：一条度量领导要的结果（不是工作量），一条守约束（指纹没变、回滚 = 0 之类）。
- 一句「每条都要在对话里贴实际命令输出（含反向验证的红→绿证据），只说做完了不算」。
- 有受阻项才建 `BLOCKED.md`，建了就随交付提交；一条都没有就不建，在收尾汇报写一句「无受阻项」。
- 止损：「或已跑满 N 轮——满轮即停，如实汇报卡在哪、还差什么」。

## 探索型：改四处

当用户要的是答案本身（调研、选型、该不该做 X），硬指标只会换来凑数的答案：

1. 完成条件换成学习目标：结论条数设上限，每条附来源与日期或可复跑的复现步骤——宁收 2 条实的，不收 10 条凑的。
2. 预算换成可承受损失：最多花多少时间、查多少来源；烧完就交卷，交「目前最优 + 还没排除什么」。
3. 防作弊主防编造：凑数结论、查无此文的引用、没跑过的「实测」都算作弊；每条结论要经得起随机抽一条、10 分钟内复现。
4. 此路不通 = 合格交付：带证据证明某方向是死路（死因 + 原始输出），按完成计。

## 从决策台账到 brief

- 台账里「谁定的 = 用户」的条目 → 写进正文，作为已定事实。
- 台账里「谁定的 = 我 / 默认」的条目 → 写进「我替领导拍的板」，标明是猜的。
- 台账里「置信度 = 低」的条目 → 要么补任务 0 去验证，要么写进风险。
- 未知项 → 要么变成任务 0，要么写进 `BLOCKED.md` 的待裁决清单。

## 发出前自检

1. ≤4000 字符？一个 `/goal`、一次粘贴？
2. 分型对吗？命令亲手跑过？没问的都写进「我替领导拍的板」并带默认值？
3. 验收全是命令？防作弊、反向验证、三道止损、`PROGRESS.md` / `BLOCKED.md` 机制齐？
4. 全文无「来找我」？大白话？零多余玩笑？
5. 交付三样齐、无过程噪音？暗卷自留没进书？
6. 多 agent：全局段齐、地界不重叠、取证不互相作废？
